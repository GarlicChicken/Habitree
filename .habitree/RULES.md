## `work` · AI가 일하는 방식

- **[권장 · quality] 결과를 확인할 기계 검증(테스트·빌드·린트 명령)을 정해 설정 `verify`에 등록하고, 고칠 때마다 돌린다.**
  - 이유: 통과·실패가 분명해야 AI가 스스로 고치고, 낮은 등급 모델의 실수도 잡힌다.
  - 점검 (눈으로): 설정의 verify에 명령이 하나 이상 있는지 본다.
  - 피드백 0 · `work.verify.define-check`

## `work/cycle` · 작업 순환: 찾기·쓰기·만들기·기록·고치기·점검

- **[권장 · process] 같은 파일을 조금씩 여러 번 고치지 않는다. 바꿀 것을 먼저 목록으로 모으고 한 번에 고친 뒤 한 번 확인한다.**
  - 이유: 고칠 때마다 파일을 다시 읽어 토큰이 들고, 고친 곳끼리 어긋나기 쉽다.
  - 점검 (눈으로): 한 파일에 작은 수정이 여러 번 이어졌는지 본다.
  - 피드백 0 · `work.cycle.batch-edits`
- **[필수 · process] 사용자 피드백은 고치는 것과 동시에 규칙으로 남긴다. 같은 뜻 규칙이 있으면 `habitree rules hit`, 없으면 `habitree rules add`(가장 넓게 맞는 범위에).**
  - 이유: 사용자가 같은 피드백을 두 번 하지 않게 한다.
  - 점검 (눈으로): 이번 피드백이 규칙 DB에 기록됐는지 본다.
  - 피드백 0 · `work.cycle.feedback-to-rule`
- **[필수 · process] 새로 만들기 전에 지도(README 색인)와 규칙에서 같은 일을 하는 문서·도구·코드가 있는지 먼저 찾는다. 있으면 쓰고, 낡았으면 그 자리에서 고친다.**
  - 이유: 같은 것을 두 번 만들면 토큰과 유지 비용이 두 배가 되고, 원본이 둘이 된다.
  - 점검 (눈으로): 새 파일·함수를 만들기 전에 찾은 근거(지도 항목, 검색 결과)를 말할 수 있는지 본다.
  - 피드백 0 · `work.cycle.find-first`
- **[권장 · structure] 같은 작업이 두 번 되풀이되면 세 번째 전에 도구·함수·양식으로 만든다.**
  - 이유: 되풀이할 때마다 같은 코드를 다시 쓰면 토큰을 매번 다시 쓰고 결과도 조금씩 달라진다.
  - 점검 (눈으로): 이번 작업에서 전에 쓴 것과 비슷한 스크립트를 새로 썼는지 본다.
  - 피드백 0 · `work.cycle.repeat-to-module`
- **[권장 · structure] 쌓는 만큼 덜어낸다. 도구·추상화·설정 층은 실제로 다시 쓰일 때만 만들고, 겹치거나 안 쓰이는 규칙·도구·코드는 합치거나 지운다.**
  - 이유: 한 번 쓰고 마는 도구와 끝없이 늘어나는 규칙은 그 자체로 짐이다. 읽을 것이 늘면 토큰과 시간이 늘어난다.
  - 점검 (눈으로): `habitree check`의 무게 줄과 `habitree refactor`의 덜어내기 제안을 본다.
  - 피드백 0 · `work.cycle.trim`
- **[필수 · quality] 끝내기 전에 `habitree check`와 등록한 검증 명령(테스트·빌드)을 실행하고, 나온 문제를 고친 뒤 끝낸다.**
  - 이유: 사람이 검사기 역할을 하면 '됐어?'를 되풀이하며 시간과 토큰이 샌다.
  - 점검 (눈으로): 끝 보고에 점검·검증 결과가 들어 있는지 본다.
  - 피드백 0 · `work.cycle.check-before-done`
- **[필수 · docs] 바꾼 것은 이어진 문서(폴더 README, 지도, 변경 기록)에 함께 반영한다.**
  - 이유: 문서가 실제와 어긋나면 다음 작업이 틀린 지도를 읽는다.
  - 점검 (눈으로): `habitree check`가 지도·링크·갱신일 문제를 보고하지 않는지 본다.
  - 피드백 0 · `work.cycle.record`
- **[권장 · docs] 발견했지만 지금 고치지 못한 문제와 아이디어는 변경 기록의 '손볼 것'에 적는다. 처리하면 지우고 기록으로 옮긴다.**
  - 이유: 적지 않으면 다음 세션이 같은 문제를 처음부터 다시 찾는다.
  - 점검 (눈으로): 작업 중 미룬 문제가 '손볼 것'에 있는지 본다.
  - 피드백 0 · `work.cycle.todo`

## `docs` · 문서와 지도

- **[필수 · docs] 도구가 만든 파일과 구역(habitree:begin/end 사이)은 직접 고치지 않는다. 원본을 고친 뒤 도구로 다시 만든다.**
  - 이유: 직접 고친 내용은 다음 생성 때 사라지거나 원본과 어긋난다.
  - 점검 (눈으로): `habitree check`의 generated.edited 알림이 없는지 본다.
  - 피드백 0 · `docs.generated-no-edit`
- **[필수 · docs] 같은 내용을 여러 곳에 복사하지 않고 원본 한 곳에 두고 링크한다.**
  - 이유: 복사본은 따로 낡아 서로 어긋난다.
  - 점검 (눈으로): 같은 설명이 두 문서에 따로 있지 않은지 본다.
  - 피드백 0 · `docs.single-source`

## `code/structure` · 코드 구조(모듈, 파일 크기, 중복)

- **[권장 · structure] 코드가 파일 하나나 함수 하나에 몰려 있으면 먼저 덜어 낼 것을 덜고, 그다음 이미 있는 경계(클래스, 같은 접두어 묶음)를 따라 한 걸음씩 옮긴다.**
  - 이유: 몰린 코드는 고칠 때마다 통째로 읽혀 토큰이 들고, 한 곳을 고치다 엉뚱한 곳이 깨지기 쉽다. 새 층을 더하는 정리는 읽을 곳을 오히려 늘린다.
  - 점검 (자동): `habitree refactor`가 파일·함수 줄 수를 프로젝트 중앙값과 견주고, git 변경 횟수로 순서를 정한다.
  - 피드백 0 · `code.structure.concentration`
- **[권장 · structure] 같은 코드가 이미 여러 곳에 있으면 한 곳을 남기고 나머지가 그곳을 부르게 바꾼 뒤 복사본을 지운다. 새 층은 남길 곳이 없을 때만 만든다.**
  - 이유: 복사본은 따로 낡아서 고칠 곳이 늘고, AI는 같은 코드를 여러 번 읽는다.
  - 점검 (자동): `habitree refactor`가 `map dupes`의 같은 몸통과 같은 글(기준 줄 수 이상)을 묶어 본다.
  - 피드백 0 · `code.structure.duplication`
- **[권장 · structure] 한 기능이 여러 파일에 흩어졌거나 쓰이지 않는 코드, 한 곳에서만 쓰는 짧은 층이 있으면 나누기보다 합치기와 지우기를 먼저 검토한다.**
  - 이유: 조각이 많을수록 한 기능을 보려고 여러 파일을 열어야 하고, 쓰이지 않는 코드도 읽을 때마다 토큰이 든다. 정적 분석이라 확실하지 않아 정보로 알린다.
  - 점검 (자동): `habitree refactor`가 참조 그래프(들어오는 참조 수, 서로 참조)와 git의 함께 바뀐 기록, 같은 이름 정의를 본다.
  - 피드백 0 · `code.structure.fragmentation`
- **[권장 · structure] 기능을 더할 때 기존 함수·파일에 덧대지 말고 역할별 모듈·함수로 나눈다. 한 파일이 계속 커지면 나눌 때다.**
  - 이유: 덧대기로 커진 코드는 읽을 때마다 토큰이 많이 들고, 고칠 때 엉뚱한 곳이 깨진다.
  - 점검 (눈으로): 이번에 크게 늘어난 파일이 있는지, 비슷한 코드가 복사됐는지 본다.
  - 피드백 0 · `code.structure.module-over-patch`

## `security` · 보안과 개인정보

- **[필수 · security] API 키·토큰·비밀번호·개인정보를 코드, 문서, 커밋에 넣지 않는다. 환경 변수나 .env(커밋 제외)로 받는다.**
  - 이유: 한 번 공개된 비밀은 지워도 이미 퍼졌을 수 있다.
  - 점검 (자동): 잘 알려진 키 형식(sk-, ghp_, AKIA, 개인 키 머리말)이 파일에 없는지 자동으로 찾는다.
  - 피드백 0 · `security.no-secrets`
